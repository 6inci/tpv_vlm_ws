# 작업 흐름 기반 실험 계획 (2026-11-20)

- 상태: **DESIGN** (계획 + 가능성 점검). 기존 코드·설정·결과·사진은 읽기만 했고, 이 폴더 밖에 쓴 파일은 없다.
- 표기: `CONFIRMED` 이번에 직접 실행·확인 / `INFERRED` 확인한 값에서 이어지는 해석 / `UNKNOWN` 미확인 / **[한계]** 지금 구조로는 안 되는 것
- 좌표: 별도 표기가 없으면 왜곡 보정된 1920×1080 사진의 픽셀(`undistorted_px`)이다.
- 점검에 쓴 사진 8장은 지금까지 개발에 쓴 사진과 같다. 아래 수치는 **가능성 점검(개발 데이터)**이며 논문 성능 수치가 아니다.
- 기준 박스(큐브 올린 팔레트 8개, 빈 팔레트 8개)는 AI가 읽은 값이고 사람이 확정하지 않았다. 이번에 대조 그림(`sim/results/slot_contact_sheet.jpg`)으로 AI가 다시 확인했다.

## 0. 대상 작업

지시 예: "하역장 옆에 있는 물체를 가져다 컨베이어 벨트 옆에 놓아줘." 움직이는 주체는 전면 그리퍼가 달린 메카넘 로봇이다.

1. 집을 물체를 찾는다(그리퍼로 잡을 수 있는 것).
2. 로봇이 갈 수 있는 영역을 정한다(5S: 노란 선 안이 주행 구역).
3. 집을 물체 앞으로 이동한다. 그리퍼가 물체를 향해야 한다.
4. 집은 뒤 놓을 곳을 다시 찾는다.
5. 놓을 곳 앞으로 이동한다. 그리퍼가 놓을 곳을 향해야 한다.

환경에서 확인된 문제는 5장에 한계로 정리했다. 핵심은 세 가지다.

- **[한계] 물체가 화면에서 너무 작다.** Qwen3-VL은 32×32 px를 토큰 하나로 본다(patch 16, merge 2). 큐브는 토큰 반 개, 팔레트는 토큰 두 개 크기다. 전체 사진에서는 두 모델 모두 16개 중 0개를 찾았다(`CONFIRMED`).
- **[한계] "하역장 옆"(트럭 앞) 자리는 지금 배치에서 로봇이 설 수 없다.** 기존 경로계획에서 트럭 앞 자리는 사진 4·6의 집기와 사진 5·7의 놓기가 모두 `NOT_FOUND`다. 왼쪽 위 모서리 자리(사진 2의 놓기, 사진 8의 집기)도 같다(`CONFIRMED`, 기존 결과).
- **[한계] 그리퍼가 닿는지 모른다.** 유효한 정차 자세에서도 차체 앞에서 목표 중심까지 9.0–14.0 cm가 남는다(`CONFIRMED`, 기존 결과). 팀원이 대략 잰 그리퍼 끝은 바퀴 중심에서 약 19.5 cm이고, 우리 차체 모델의 앞면은 17.5 cm다. 이 값대로면 7–12 cm가 모자란다(`INFERRED`). 반면 실제 주행에서는 그리퍼가 큐브를 3.3 cm 밀었다고 했으므로 두 값이 서로 맞지 않는다(`UNKNOWN`).

## 2. 가능성 점검 결과 (이번에 실행)

실행 스크립트와 결과는 6장에 있다. 모델은 로컬 캐시만 썼고 설치·다운로드는 없다.

### 2.1 기준 시설 찾기 (전체 사진, Qwen3-VL-4B)

- 트럭, 하역 구획, 컨베이어, 충전소, 보행로, 이동로봇 6종을 8장 모두에서 찾았다. 박스가 8장 사이에서 거의 같다(예: 트럭 [1444–1446, 0, 1686–1690, 153–156]).
- 이동로봇 박스는 8장 모두 로봇 위에 있다(예: [1584, 624, 1818, 778]). 이전 실험에서 로봇을 트럭으로 부른 문제는, "바닥을 달리는 바퀴 달린 차량(고정 로봇팔 아님)"이라는 정의를 주자 나타나지 않았다.
- 호출당 약 11 s, 입력 약 2,250 토큰.
- 정답 박스가 없어 IoU는 계산하지 않았다. AI가 좌표를 사진과 대조해 확인했다.

### 2.2 작은 물체 찾기

기준 물체 16개(큐브 올린 팔레트 8, 빈 팔레트 8). 사진마다 480×270 px 창 6개를 4배로 확대해 물었다(48회 호출).

| 모델 | 입력 | 프롬프트 | 큐브 올린 팔레트 | 빈 팔레트 | 잘못 낸 항목 |
|---|---|---|---|---|---|
| 4B | 전체 사진 | 일반 | 0/8 | 0/8 | 0 |
| 8B 4-bit | 전체 사진 | 일반 | 0/8 | 0/8 | 0 |
| 4B | 4배 확대 | 일반("pallet") | 1/8 | 0/8 | 0 |
| 8B 4-bit | 4배 확대 | 일반 | 7/8 (종류 맞음 5) | 0/8 | 32 |
| 4B | 4배 확대 | 현장 설명 v2 | 8/8 | 5/8 (상태 맞음 3) | 36 |
| 8B 4-bit | 4배 확대 | 현장 설명 v2 | 8/8 | 5/8 | 29 |
| 4B | 4배 확대 | 현장 설명 v3 | 8/8 | 7/8 | 39 |
| 8B 4-bit | 4배 확대 | 현장 설명 v3 | 7/8 (종류 맞음 6) | 7/8 | 68 |

- "현장 설명"은 "이 현장의 소형 팔레트는 회색 격자 판이고 위에서 보면 작은 격자 덮개처럼 보인다"는 문장이다. v3는 여기에 화면에서의 크기(그림 폭의 약 1/10)와 "회색 판만", "한 번만"을 더했다.
- 찾은 박스는 정확하다. 예: 기준 [422, 410, 468, 449]에 대해 모델 [420, 408, 467, 449].
- 잘못 낸 항목은 매번 같은 고정 설비다: 충전소 기둥, 빨간 소화기 받침, 왼쪽 아래 회색 선반.
- 8B가 4B보다 낫지 않다. 잘못 낸 항목이 더 많고 느리다.
- v3는 4B v2 결과를 본 뒤 같은 사진으로 고친 문구다. 개발 조정이지 평가가 아니다.

### 2.3 모델 출력 + Python 검사

모델이 낸 박스에 Python 검사 세 가지를 적용했다. 검사 기준은 결과를 본 뒤 정했다(`POST_HOC`).

- 크기: 가로·세로 30–75 px
- 색: 회색 판 픽셀 비율 ≥ 0.35
- 배경 대비 변화: 나머지 7장의 중앙값 배경과 다른 픽셀 비율 ≥ 0.30
- 적재 상태: 박스 안 빨간 픽셀 수 ≥ 40이면 적재, 아니면 빔(모델의 상태 답은 쓰지 않음)

| 모델·프롬프트 | 검사 전 잘못 낸 항목 | 검사 후 잘못 낸 항목 | 검사 후 찾은 기준 물체 (상태까지 맞음) |
|---|---|---|---|
| 4B v2 | 36 | 0 | 13/16 |
| 4B v3 | 39 | 0 | **15/16** |
| 8B v2 | 29 | 0 | 13/16 |
| 8B v3 | 68 | 0 | 14/16 |

- 배경 대비 변화 비율이 가장 잘 갈랐다. 진짜 물체는 0.70–0.82, 잘못 낸 항목은 0.00–0.22다.
- 사진 1의 왼쪽 아래 빈 팔레트는 네 조합 모두 놓쳤다(선반 그림자 안).
- **[한계]** 배경은 같은 날 찍은 나머지 7장으로 만들었다. 실제 운용에는 물체를 모두 치운 기준 사진이 필요하다.
- **[한계]** 확대 창 6개의 위치는 물체가 놓이는 자리를 알고 정했다. 실제 흐름에서는 기준 시설 박스에서 창을 만들어야 하고, 그 연결은 아직 실행하지 않았다.

### 2.4 주행 영역

- **모델에게 물은 경우**(4B, 사진 1·5·8): 5S 설명이 없어도 3회 모두 "노란 선이 주행 영역의 경계"라고 답했다. 그러나 박스는 믿을 수 없다. 설명 없이는 3회 중 2회가 사진 전체였고, 5S 설명을 주면 2회는 위·아래·오른쪽이 맞고 왼쪽이 약 300 px 넓었으며 1회는 트럭 구역을 가리켰다.
- **선으로 계산한 경우**(CPU): 밝은 테이프를 장벽으로 보고 로봇 위치에서 이어진 바닥을 주행 영역으로 잡으면, 8장 모두 사람이 그린 초안과 IoU 0.86이다. 상자 더미 구획은 맞게 빠졌지만 적치 구역은 테이프가 끊겨 안쪽이 주행 영역으로 새어 들어갔다.
- 노란색만 골라내는 방식은 실패했다. 테이프 채도가 29–127로 낮고 오른쪽 경계는 줄무늬 테이프다.
- 결론: 모델은 "어떤 표시가 경계인가"라는 규칙은 말할 수 있지만 영역 모양은 못 만든다. 영역 모양은 사람이 확인한 정적 지도가 맡아야 한다.

## 3. 모델 조합

DINO, SigLIP2, 8B 모델은 쓰지 않는다. Qwen3-VL-4B 하나와 Python이면 된다. 모델을 번갈아 올릴 필요가 없어진다.

| 단계 | 담당 | 입력 → 출력 | 상태 |
|---|---|---|---|
| S0 준비(1회) | 사람 + Python | 왜곡 보정, 바닥 좌표(팀원 지도와 통일), 정적 지도, 물체를 치운 기준 사진 | 지도 통일과 기준 사진 필요 |
| S1 지시 해석 | Qwen 4B (글자만) | 지시문 → 집을 물체, 출발 기준 시설·관계, 놓을 곳 기준 시설·관계 | 기존 `task_context_v1` 재사용 가능 |
| S2 기준 시설 찾기 | Qwen 4B (전체 사진) | 기준 시설 이름 → 박스, 이동로봇 박스 | 2.1에서 확인 |
| S3 확대 창 만들기 | Python | 시설 박스 + 관계("옆") → 480×270 px 창, 4배 확대 | 미실행 |
| S4 작은 물체 제안 | Qwen 4B (확대 창) | 창 → 팔레트 박스와 종류 | 2.2에서 확인 |
| S5 검사 | Python | 크기(cm), 색, 기준 사진 대비 변화, 빨간 픽셀로 적재 상태, 중복 제거 | 2.3에서 확인 (사후 기준) |
| S6 대상 선택 | Python | 지시의 관계에 맞는 물체 하나. 둘 이상이면 `AMBIGUOUS`, 없으면 `NOT_FOUND` | 미실행 |
| S7 놓을 곳 | Python + (선택) Qwen | 빈 팔레트면 S4–S6 반복. 빈 바닥이면 Python이 후보 지점을 만들고 Qwen이 금지 구역 여부만 판단 | 미실행 |
| S8 경로·자세 | 기존 통합 경로계획 | 바퀴는 주행 영역 안, 차체 방향 0/90/180/270° 중 그리퍼가 목표를 향하는 자세, 경로 A·B | 기존 코드 |
| S9 다시 보기 | S2–S5 반복 | 집은 뒤 새 사진: 출발 자리 팔레트가 "빔"으로 바뀌었는지, 놓은 뒤 목표 자리에 큐브가 있는지 | 미실행 |

로봇의 위치와 방향은 모델이 정하지 않는다. 모델은 로봇 박스만 주고, 방향은 팀원의 ArUco 위치추정이 줘야 한다.

## 5. 코멘트

### 5.1 한계 (지금 구조로는 안 되는 것)

1. **[한계] 전체 사진 한 장으로 작은 물체를 찾는 것은 안 된다.** 두 모델 모두 0/16. 모델 크기를 키워도 해결되지 않는다. 확대가 필수다.
2. **[한계] 모델 출력만으로는 쓸 수 없다.** 확대해도 48개 창에서 잘못 낸 항목이 29–68개다. Python 검사가 없으면 고정 설비를 물체로 집는다.
3. **[한계] "팔레트"라는 단어로는 못 찾는다.** 일반 문구로는 4B가 1/16이다. 이 팔레트는 위에서 보면 격자 덮개로 보인다. 현장 설명 문장이 필요하고, 논문에서는 이를 "사람이 준 현장 지식"으로 밝혀야 한다. 모델의 자율 추론이라고 쓸 수 없다.
4. **[한계] 주행 영역의 모양은 모델이 만들 수 없다.** 박스조차 3회 중 1–2회 틀렸다. 정적 지도가 필요하다.
5. **[한계] 예시 지시("하역장 옆 물체")는 지금 배치에서 경로계획이 실패한다.** 트럭 앞 자리는 오른쪽 경계와의 옆 공간이 9 cm인데 필요한 값은 14.35 cm다. 인식이 다 맞아도 경로가 없다.
6. **[한계] 파지·배치 성공은 주장할 수 없다.** 그리퍼 도달 거리, 무엇을 잡는지, 높이 간섭이 모두 미측정이다.
7. **[한계] 두 좌표계가 1–9.5 cm 다르다.** 어느 쪽이 맞는지는 줄자로 재야 안다. 통일 전에는 cm 수치를 논문에 쓸 수 없다.
8. **[한계] 이번 수치는 일반화되지 않는다.** 사진 8장, 배치 1개, 자리 6곳, AI가 읽은 기준 박스, 같은 사진으로 고친 프롬프트와 검사 기준이다.
9. **[한계] 로봇 방향은 사진에서 나오지 않는다.** 모델은 박스만 준다. 팀원의 위치추정이 없으면 S8의 시작 자세를 사람이 넣어야 한다.
10. **[한계] 큐브는 팔레트 위에 떠 있다.** 컨베이어 받침처럼 높은 곳의 물체는 바닥 좌표가 높이만큼 어긋난다.

### 5.2 의문점 (사용자 결정 필요)

1. 그리퍼가 잡는 것은 큐브인가, 큐브가 올라간 팔레트인가? 검사 기준과 정차 거리가 달라진다.
2. "컨베이어 벨트 옆에 놓아줘"의 놓을 곳은 빈 팔레트인가, 빈 바닥인가? 빈 팔레트가 없는 사진(6번)이 있다.
3. "하역장 옆"은 어디까지인가? 트럭 앞 자리만인가, 콘 줄 옆 자리(트럭에서 약 70 cm)도 포함하는가?
4. 실험은 사진 한 장으로 A·B를 모두 정하는 방식인가, 집은 뒤 다시 찍어 놓을 곳을 정하는 방식인가? 사용자가 말한 흐름은 뒤쪽이다. 뒤쪽이면 팀원과 사진을 주고받는 절차가 필요하다.
5. 아래 가운데의 큰 회색 격자판(약 120 px)은 팔레트인가 바닥 덮개인가? 지금은 방해 물체로 둔다.

### 5.3 제안

1. **자리 옮기기.** 트럭 앞 자리를 오른쪽 경계에서 6 cm 이상 왼쪽으로 옮긴다. 옮긴 뒤 기존 경로계획으로 다시 확인해야 한다(`UNVERIFIED`).
2. **그리퍼 실측 1회.** 차체 앞에서 그리퍼 끝까지, 잡을 수 있는 폭, 잡는 높이. 이 값이 없으면 S8 결과는 계속 "가정 조건부"다.
3. **기준 사진 촬영.** 큐브와 소형 팔레트를 모두 치운 사진 1장. S5의 배경으로 쓴다.
4. **새 사진으로 평가.** 지금 8장은 개발용으로만 쓴다. 프롬프트와 기준값을 고정한 뒤 새로 찍는다. 물체가 없는 경우, 큐브가 둘인 경우, 빨간 방해 물체가 있는 경우를 넣는다. 기준 박스는 실행 전에 사람이 확정한다.
5. **5S는 "주행 영역 찾기"가 아니라 "놓아도 되는 곳 판단"에서 시험한다.** 주행 경계는 5S 설명 없이도 3회 모두 노란 선이라고 답해 차이를 볼 수 없다. 이전 실험에서 규칙이 없을 때 보행자 통로를 놓을 곳으로 고른 사례가 있으므로, 차이가 날 수 있는 곳은 배치 판단이다.
6. **집기·놓기 확인을 빨간 픽셀 상태 변화로 한다.** 출발 자리가 "적재 → 빔", 목표 자리가 "빔 → 적재"로 바뀌면 성공이다. 이번 점검에서 상태 판정은 찾은 물체 전부에서 맞았다.
7. **팔레트를 눈에 띄는 색으로 바꾸는 것은 선택 사항이다.** 바꾸면 현장 설명 없이 찾을 가능성이 있지만 확인하지 않았다(`UNKNOWN`). 바꾸지 않으면 현장 설명을 조건으로 명시하면 된다.
