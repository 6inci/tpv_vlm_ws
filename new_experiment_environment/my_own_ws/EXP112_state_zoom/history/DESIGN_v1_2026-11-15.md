## 1. 왜 하는가

- EXP120 oracle에서 J-vlm(전체 이미지)은 정답 후보를 받고도 상태 질의 12개 중 6개만 맞혔다.
  - "빈 팔레트"는 4장 모두 고르지 못했다.
  - 번호 상자 색은 원인이 아니었다 (D1).
- 전체 이미지에서 블록은 0.5–0.8토큰(1토큰 = 32×32 px)이다. 해상도 한계 가설이 남아 있다 (INFERRED).
- EXP111은 확대 crop에서 블록을 찾는 방식으로 상태를 맞혔다. 이번 실험은 **VLM이 직접** 상태를 판단할 때도 확대가 효과가 있는지를 본다.
- 8B 재검토 조건과의 관계
  - 사용자 조건: 정확한 후보를 받아도 4B가 반복 실패하면 8B를 다시 본다.
  - 이 실험의 oracle 결과가 그 판단 근거 중 하나가 된다.

## 2. 가설 (실행 전에 고정)

| ID | 가설 | 예측 |
|---|---|---|
| H-zoom1 | 확대 이미지를 주면 상태 판단(빈/적재)이 나아진다 | Z-crop 정확도 > Z-full |
| H-zoom2 | 전체 이미지를 함께 주면 적재 관계(위 / 옆 바닥) 판단이 낫다 | Z-both의 "바닥 블록을 위라고 함" < Z-crop |
| H-zoom3 (위험) | 확대 이미지에는 팔레트 옆 바닥 블록도 크게 보여서, 이를 "위에 있음"으로 잘못 볼 수 있다 | Z-crop의 도전 조건 오류가 Z-full보다 많을 수 있음 |

## 3. 조건

같은 모델, 같은 후보, 같은 질문. 주는 이미지만 다르다.

| 조건 | 모델에 주는 것 | 팔레트를 가리키는 말 |
|---|---|---|
| Z-full | 전체 이미지 1장. 모든 후보에 흰색 번호 상자 | "box number k" |
| Z-crop | 해당 팔레트 확대 이미지 1장. 상자를 그리지 않음 | "the pallet at the center of this image" |
| Z-both | 전체 이미지(흰색 번호 상자) + 해당 팔레트 확대 이미지, 2장 | "box number k in the first image; the second image is an enlarged view of the same pallet" |

- 확대 규칙: EXP111 s3 / EXP110 X4와 같다 (주변 3배, 최소 한 변 160 px, 긴 변을 768 px로 확대). H-zoom 전에 이미 정해진 값이다.
- 상자 색: 흰색으로 고정한다 (EXP120 D1과 같은 그리기). 블록 색과 겹치지 않게 하려는 설계상 선택이다. D1 결과에 맞춘 것이 아니다.
- 질문 (팔레트마다 1회, 초안. 실행 전 `config.json`에 고정)
  - `Look at the small pallet {where}. Which blocks are lying on top of this pallet? Count only blocks that sit on the pallet surface, not blocks on the floor next to it. Return JSON only: {"blocks_on_pallet": [<"red" or "blue">, ...]} (an empty list if the pallet is empty).`
  - 상태 = 목록이 비어 있지 않으면 적재. 색 = 목록의 색 집합.
  - 형식 검사: JSON 객체, `blocks_on_pallet` 키, 문자열 목록. red/blue가 아닌 색은 형식 오류가 아니라 색 오답으로 센다.
- 후보 출처 (결과 표와 보고서에서 항상 따로 적는다)
  - **oracle = 진단 결과**
    - 정답 소형 팔레트 박스를 쓴다. 탐지 오류를 빼고 상태 판단만 본다.
    - 가설(H-zoom) 판단은 이 조건으로 한다. 시스템 성능으로 보고하지 않는다.
  - **detected = 시스템 결과**
    - EXP111이 새 dev에서 예측한 팔레트를 쓴다. 오탐 후보도 그대로 들어간다.
    - 시스템 충분성은 이 조건으로 본다.
    - EXP111이 PASS 전이면 AGENTS 규칙상 제한적 예외가 필요하다. **사용자 승인 필요** (E3a 때의 승인은 E3a에 한정되었다).
- 비교 기준선
  - B-rule: EXP111 결정론 상태 규칙 (확대 crop에서 DINO 블록 질의 + 중심점 규칙). 같은 새 dev에 적용한다.
  - B-const: 항상 "빈" 또는 항상 "적재"라고 답하는 경우. 우연 수준을 보여 준다.
- 보조 분석 (목적 객체 선택과의 연결): 팔레트별 상태 답에서 Python이 e03/e04/e05형 선택(빈, 블록 있는, 파란 블록 있는)을 계산한다. 이를 EXP120의 J-vlm 직접 선택과 비교한다. 역할 경계에 따라 VLM은 상태 라벨만 내고, 선택 계산은 Python이 한다.

## 6. P01–P04에 맞추지 않기 위한 규칙

- P01–P04는 **코드 동작 확인(smoke test)에만** 쓴다. 확인 항목:
  - 실행되는가
  - JSON 형식이 맞는가
  - 2장 입력(Z-both)이 GPU 메모리에 들어가는가
- smoke 모드는 정답 파일을 읽지 않는다. 정확도를 계산하지 않는다.
- 질문 문장, 확대 규칙, 상자 그리기는 새 dev 실행 전에 `config.json`에 고정한다.
  - 새 dev 결과를 본 뒤 바꾸면, 새 판(version)으로 기록하고 바꾼 이유를 적는다.
  - 바뀐 판의 효과는 같은 dev 숫자로 주장하지 않는다.
- 새 dev는 조건마다 1회 실행한다. 같은 dev에서 설정을 여러 번 바꿔 가며 가장 좋은 값을 고르지 않는다.

## 7. 실행 순서 (예정)

1. EXP111 새 촬영 → 카메라 확인 → dev 8배치 → test 16배치와 봉인
2. 새 dev 정답 작성과 사람 검토 (팔레트, 블록, 바닥 블록 유무)
3. EXP112 코드 작성 → P01–P04 smoke test (형식과 메모리만)
4. 설정 고정 (`config.json`, sha256)
5. 새 dev에서 Z-full, Z-crop, Z-both, B-rule 각 1회 실행
6. 보고: 수행 완료와 가설 지지 여부를 분리하고, CONFIRMED / INFERRED / UNKNOWN을 표기
7. 이어서 EXP120 관계 질의를 새 dev에서 다시 본다 (상태 판단 결과를 반영한 조건 포함)

## 9. 종료 기준 (실행 전에 고정)

- **정상 종료**
  - 새 dev에서 oracle 후보로 Z-full, Z-crop, Z-both, B-rule을 각 1회 실행하고, 채점하고, 보고하면 끝난다.
  - detected 조건은 승인되면 같은 방식으로 1회 실행한다.
- **변형 금지**
  - 결과와 상관없이, 같은 데이터에서 확대 배율, 질문 문장, 상자 그리기, 모델을 바꾼 추가 실행을 하지 않는다.
  - 변형이 필요하면 §0의 네 요건을 갖춘 새 제안으로 사용자 승인을 받는다.
- **조건 하나가 실행 불가인 경우**
  - 예: Z-both가 메모리 초과나 형식 오류로 돌지 않는 경우.
  - 그 사실을 기록하고, 설정을 바꾸지 않은 채 나머지 조건으로 종료한다.
- **test**: 설정을 확정하고 사용자가 승인한 뒤 1회만 실행한다.
