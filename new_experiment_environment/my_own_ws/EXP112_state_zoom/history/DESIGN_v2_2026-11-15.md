## 0. 제안 요건

| 요건 | 내용 |
|---|---|
| 기존 연구 가설과의 관계 | 핵심 질문: "VLM이 객체의 상태와 공간 관계를 이해해 올바른 목적 객체를 고를 수 있는가". 그 첫 단계인 **상태 판단**만 떼어 검증한다. EXP120 oracle J-vlm의 상태 실패(6/12, "빈" 0/4)가 해상도 때문인지 가린다 |

| 평가 기준 | §5 지표. 판정 규칙은 `CRITERIA_REVIEW.md` |
| 종료 기준 | §9 |

## 1. 왜 하는가

- EXP120 oracle에서 전체 이미지만 본 J-vlm은 정답 후보를 받고도 상태 질의 12개 중 6개만 맞혔다. 이는 우연 수준이다.
- 번호 상자 색은 원인이 아니었다 (EXP120 D1).
- 전체 이미지에서 블록은 0.5–0.8토큰이다 (1토큰 = 32×32 px). 해상도 한계 가설이 남아 있다 (INFERRED).

## 2. 가설 (실행 전 고정)

|---|---|---|

## 3. 조건별 입력, 평가 대상, 실행 횟수, 기록

공통 사항
- 이미지: 새 dev D01–D08, 배치당 프레임 3장. PNG, 왜곡 보정 전 원본 1920×1080.
- 후보: **정답 소형 팔레트 박스 (oracle)**. 번호는 배치 안에서 왼쪽부터 1, 2.
- 모델: M1 4B BF16, greedy (do_sample=False).
- 각 조건은 **1회 실행.** 1회 = 팔레트 16개 × 프레임 3장.

| 조건 | 모델 입력 | 질문과 출력 | 1회 호출 수 | 평가 대상 |
|---|---|---|---|---|
| Z-full | 전체 이미지 1장. 모든 후보에 흰색 번호 상자 | 팔레트별 질문 (아래). `{"blocks_on_pallet": [...]}` | 48 | 상태, 색, 적재 관계 |
| Z-crop | 해당 팔레트 확대 이미지 1장 (주변 3배, 최소 160 px, 긴 변 768 px). 상자 없음 | 같음 | 48 | 같음 |
| Z-both | 전체 이미지(흰색 번호 상자) + 해당 팔레트 확대 이미지, 2장 | 같음 | 48 | 같음 |
| B-rule (기준선) | Z-crop과 같은 확대 이미지 | Qwen이 블록 **박스**를 낸다(EXP110 C1 프롬프트, 영어 질의 q029 block, q031 blue block, q033 red block, q035 cube). Python이 판정: 블록 박스 중심이 팔레트 안이면 적재, 색은 q031/q033 결과. EXP111 s4 규칙 그대로 | 192 (16 × 3 × 4) | 같음 |
| B-const (기준선) | 없음 (계산만) | 항상 "빈" 또는 항상 "적재" | 0 | 상태 |

- 팔레트별 질문 (실행 전 `config.json`에 고정, 초안)
  - `Look at the small pallet {where}. Which blocks are lying on top of this pallet? Count only blocks that sit on the pallet surface, not blocks on the floor next to it. Return JSON only: {"blocks_on_pallet": [<"red" or "blue">, ...]} (an empty list if the pallet is empty).`
  - `{where}`
    - Z-full: "marked with box number k in the image"
    - Z-crop: "at the center of this image"
    - Z-both: "marked with box number k in the first image; the second image is an enlarged view of the same pallet"
- 출력 해석
  - 상태: 목록이 비어 있지 않으면 적재, 비어 있으면 빈.
  - 색: 목록의 색 집합.
  - 형식 검사: JSON 객체여야 하고, `blocks_on_pallet` 키가 있어야 하며, 값은 문자열 목록이어야 한다. 위반하면 형식 오류다.
  - red, blue가 아닌 색은 형식 오류가 아니라 색 오답으로 센다.
- 실행마다 남기는 기록

| 파일 | 내용 |
|---|---|
| `MANIFEST.json` | 실험 ID, 조건, 시작·종료 시각, sha256(코드, config, 질문 문장, 정답 파일, 이미지 봉인 목록), 환경(torch, transformers, GPU), 모델 revision, 확대 규칙 |
| `calls.jsonl` | 호출마다: 배치, 프레임, 팔레트 번호, 원문 응답, 해석 결과, 형식 오류 내용, 시간, 입력·생성 토큰 수 |
| `errors.json` | 형식 오류와 예외 전체 (원인 포함) |
| `scored.json`, `summary.json`, `SUMMARY.md` | 채점 (저장된 원자료에서 다시 계산 가능) |
| `failures/` | 틀린 팔레트마다 확대 그림, 모델 답, 정답 (개별 실패 사례) |
| 로그 | GPU 최대 사용량, 전체 시간 |

## 6. P01–P04 사용 규칙 (맞추기 방지)

- 코드 동작 확인(smoke test)에만 쓴다. 확인하는 것:
  - 실행되는가
  - JSON 형식이 맞는가
  - Z-both의 2장 입력이 GPU 메모리에 들어가는가
- smoke test의 후보는 EXP111이 P01–P04에서 예측한 팔레트를 쓴다. 정답 파일은 읽지 않고, 정확도도 계산하지 않는다.
- smoke 결과는 형식 오류 수, 토큰 수, 메모리만 출력한다. 모델 답 내용은 화면에 내지 않는다(파일에만 저장).
- 질문 문장, 확대 규칙, 상자 그리기는 새 dev 실행 전에 고정한다.
  - 새 dev 결과를 본 뒤 바꾸면 새 판으로 기록한다.
  - 바뀐 판의 효과는 같은 dev 숫자로 주장하지 않는다.

## 12. v1에서 바뀐 점

- B-rule 설명을 정정했다.
  - v1: "DINO 블록 질의 + 중심점 규칙"
  - 실제: 확대 이미지에서 Qwen이 블록 박스를 내고, Python이 중심점 규칙으로 판정한다 (EXP111 s4 코드 확인).
- detected 조건을 실행 대상에서 뺐다 (사용자 결정).
- 조건별 입력, 평가 대상, 실행 횟수, 기록을 표로 정리했다 (§3).
- 완료 상태 두 가지를 구분했다 (§7).
- 빈 팔레트 오적재를 따로 보고하는 지표로 넣었다 (§5).
- H-zoom2, H-zoom3는 기술 통계와 실패 사례만 보고한다 (§2).
- 실행 순서를 사용자 작업과 함께 정리했다 (§10).
