## Part 3. 추천 시스템 구조

**결론: 사용자가 생각한 파이프라인의 뼈대는 유지하고, 세 곳을 고친다.** 조건 도출을 상태 파악보다 앞에 두고, "기하학적 검증"을 둘로 나누고, 모든 단계에 보류 출구를 둔다. 핵심 연구 대상인 "작업 의미를 해석해 목적지 조건을 도출하는 과정"은 ①단계로 독립시켜, 그 산출물을 따로 채점할 수 있게 한다.

### 3.1 구조

```text
작업 지시 ℓ ─────► ① 조건 도출 [VLM] ─────► 목적지 조건 명세 C(ℓ)
                                             (대상 종류, 상태, 관계, 전제 조건, 영상으로 확인할 수 없는 정보)
                                                      │
고정 카메라 영상 s ─► ② 후보 생성 ──────────────────────┤   과제와 무관하게 같은 후보 목록
                     [사전 지도: 고정 시설] + [Detector: 이동 물체]
                                                      ▼
                    ③ 조건 검증
                       · 종류   : 지도·검출 라벨과 대조          [Python]
                       · 상태   : 후보 확대 영상에 예/아니오/불확실 질문 [VLM]
                       · 관계   : 박스(이후 바닥 좌표) 계산        [Python]
                       · 전제   : 다른 객체의 상태 (예: 트럭 적재함의 화물) [VLM + Python]
                                                      ▼
                    ④ 선택 또는 보류 [Python]
                       만족 후보 1개 → 선택 / 0개 → 없음 / 2개 이상 → 모호 / 검증 불가 → 확인 불가
                                                      ▼
                    ⑤ 접근 목표점 [Python] ─► ⑥ 경로 [A*] ─► (팀원) 제어
```

### 3.2 역할 구분

| 구성요소 | 맡는 일 | 맡지 않는 일 | 근거 |
|---|---|---|---|
| VLM (Qwen3-VL) | ① 지시문에서 목적지 조건을 도출한다. ③ 조건이 요구하는 상태를 후보 확대 영상에서 확인한다 | 공간 관계 판정, 좌표 계산, 기준 물체의 존재 판정, 최종 선택 | EXP120: 전체 화면 관계·상태 직접 판단은 24항목 중 15개 정답, 잘못된 선택 4건 (oracle 후보). 없는 기준 물체에 2/4 선택 `CONFIRMED` |
| Detector (Grounding DINO + EXP111 확인 단계) | ② 이동 물체(소형 팔레트, 블록)의 후보 박스를 만든다 | 과제 해석, 상태 판단, 존재 여부의 최종 판정 | EXP120 J-gate: detector만으로 한 존재 확인은 오선택을 하나도 막지 못했다 (트럭을 "forklift"로 검출) `CONFIRMED` |
| 사전 지도 (M00 촬영으로 작성) | ② 고정 시설의 번호, 박스, 종류 이름을 준다. 주행 가능 영역을 준다 | 시설의 기능 이름("하역장")과 현재 상태 | 계획서 v3 §8.1–8.2의 정보 제공 원칙 `CONFIRMED` |
| Python | ③ 관계 계산, ④ 선택·보류, ⑤ 목표점, 좌표 변환, 스키마 검증 | 지시문 해석 | 루트 AGENTS.md: 결정론적 계산은 Python에서 한다 `CONFIRMED` |
| 경로계획 (A*) | ⑥ 주행 가능 영역에서 충돌 없는 경로 | 목적지 결정 | legacy `planning/grid_astar.py`의 `plan_path` 재사용 (합성 장애물에서만 검증됨) `CONFIRMED` |

- VLM은 좌표, 경로, 모터 명령을 만들지 않는다. 이는 AGENTS.md의 역할 경계와 같다.

### 3.3 사용자 파이프라인과 다른 점

| 사용자 안 | 수정안 | 이유 |
|---|---|---|
| 작업 의도 해석 → 환경 객체 및 상태 파악 → 작업 수행 조건 추론 | **조건 도출(①)을 상태 파악(③)보다 앞에** 둔다 | 조건이 먼저 있어야 "어떤 상태를 확인할지"가 정해진다. 장면 전체의 상태를 미리 다 파악하게 하면 소형 물체 인식 실패(EXP111)가 모든 과제에 번진다 |
| 후보 목적지 생성 → 기하학적 검증 | 검증을 **조건 검증(③)**과 **실행 가능성 검증(⑤의 일부)**으로 나눈다 | "조건에 맞는 곳인가"와 "로봇이 갈 수 있는 곳인가"는 다른 질문이고, 틀리는 원인도 다르다 |
| (보류 단계 없음) | ①–⑤ 모두 보류를 출력할 수 있다. 보류 사유를 네 가지로 구분한다 | 정답이 없거나 정보가 부족한 지시에서 로봇이 엉뚱한 곳으로 가는 것을 막는다. 기존 6분류 채점(EXP120)을 그대로 쓴다 |
| VLM이 영상과 지시문을 함께 해석 | ①은 기본적으로 **지시문과 현장 어휘만** 받는다. 영상은 ③에서 쓴다. "①에 영상도 준다"는 부 조건으로 비교한다 | 조건 C(ℓ)는 정의상 장면과 무관해야 따로 채점할 수 있다. 영상이 조건 도출에 도움이 되는지는 가정하지 않고 측정한다 (Part 6, Q6) |

- 마지막 행은 사용자 결정이 필요하다. "①에 영상을 준다"를 주 조건으로 삼을 수도 있다. 그 경우에도 다른 쪽을 부 조건으로 함께 돌린다. 추가 비용은 지시문당 호출 1회다.

### 3.4 목적지 조건 명세 (①의 출력, PROPOSED)

- 닫힌 형식의 JSON이다. 자동으로 채점할 수 있게 값의 종류를 제한한다.
- 기존 EXP120 parser 형식 `{target, relation, reference, color}`를 넓힌 것이다.

```json
{
  "task_summary": "트럭에서 내린 화물을 받아 둘 자리",
  "destination": {"kind": "small pallet"},
  "conditions": [
    {"on": "destination", "type": "state", "value": "empty"},
    {"on": "destination", "type": "relation", "relation": "next_to", "reference": "truck"}
  ],
  "preconditions": [
    {"entity": "truck", "type": "state", "value": "has_cargo"}
  ],
  "unverifiable": [],
  "instruction_ambiguity": null
}
```

| 항목 | 허용 값 (초안) |
|---|---|
| `destination.kind`, `entity`, `reference` | 현장 어휘의 종류 이름 (EXP120 `config.json`의 `site_vocabulary` 확장) |
| 상태 `value` | `empty`, `loaded`, `has_cargo`, `no_cargo`, `free`, `occupied`, `on_floor`, `has_color` (+ `color`) |
| 관계 `relation` | `next_to`, `closest_to` (정의는 EXP120 `RELATION_DEFINITIONS.md`) |
| `unverifiable` | 과제에 필요하지만 영상으로 알 수 없는 정보를 자유 문장으로 적는다 (예: "출고 예약 여부") |
| `instruction_ambiguity` | 지시문 자체가 둘 이상으로 읽히면 그 이유 |

- 상태 값마다 확인 질문 문장을 하나씩 미리 고정한다. 예: `has_cargo` → "Is there any cargo on the cargo bed of this truck? Answer yes, no, or unsure."
- 이 질문 문장은 TC-cond와 TC-rule이 똑같이 쓴다. 두 방법의 차이는 "누가 조건을 정했는가"뿐이다.

### 3.5 한 가지 예 (PROPOSED 배치 XT01: 트럭 상자 있음, 팔레트 A는 트럭 옆 빈 것, 팔레트 B는 컨베이어 옆 적재)

| 단계 | W03 "트럭에서 내린 화물을 받아 둘 자리로 가." |
|---|---|
| ① | 대상 = 소형 팔레트, 조건 = 빈 ∧ 트럭 옆, 전제 = 트럭 적재함에 화물 있음 |
| ② | 후보: 지도에서 트럭·충전 패드 등, detector에서 팔레트 2개 |
| ③ | 트럭 확대 영상 "화물 있음?" → 예. 팔레트 1 "비어 있음?" → 예. 팔레트 2 → 아니오. 팔레트 1–트럭 간격 → 옆 |
| ④ | 만족 후보 1개 → 팔레트 1 선택 |
| ⑤–⑥ | 팔레트 1 접근 띠 안의 주행 가능 지점 → A* 경로 |
| 같은 배치에서 트럭 상자만 없앤 XT02 | ③에서 전제 불성립 → ④ "없음 (내릴 화물이 없음)" |

## Part 4. 핵심 연구 가설

**결론: 핵심 가설은 "장면의 작업 관련 상태만 바뀌었을 때 목적지를 올바르게 바꾸는가"로 둔다.** 조회표나 언어 사전 지식으로는 이 검사를 통과할 수 없기 때문이다. 보조 가설 세 개가 그 원인을 나눠서 본다.

### 4.1 가설

| ID | 가설 | 주 지표 | 비교 |
|---|---|---|---|
| **H0 (핵심)** | 목적지가 명시되지 않은 작업 지시에서, VLM이 도출한 조건을 현재 장면에서 검증해 고르는 구조(TC-cond)는 같은 VLM이 한 번에 고르는 방식(TC-direct)보다 **장면 쌍 정답률**이 높다. 잘못된 목적지 비율은 더 높지 않다 | 장면 쌍 정답률 (Part 7) | TC-cond vs TC-direct. 같은 영상, 같은 후보, 같은 모델 |
| H1 (조건 도출) | VLM이 도출한 조건 집합은 사전에 사람이 정의한 조건과 일치한다. 규칙표에 없는 과제 유형에서는 VLM이 규칙표(TC-rule)보다 높다 | 조건 집합 완전 일치율 | TC-cond의 ① vs TC-rule의 규칙표. 등록 과제와 미등록 과제를 따로 |
| H2 (장면 근거 사용) | 평소라면 정답일 장소가 현재 상태 때문에 무효인 항목에서, TC-cond는 그 장소를 고르지 않는다 | 사전 지식 일치 오류 비율, 근거 필요성 (Part 7) | TC-cond vs TC-direct vs TC-blind |
| H3 (보류) | 없음·모호·확인 불가 항목에서 TC-cond는 TC-direct보다 "정답이 없는데 선택"이 적다. 답할 수 있는 항목을 놓치는 일은 사전에 정한 한도를 넘지 않는다 | 정답 없는데 선택 비율, 놓침 비율 | TC-cond vs TC-direct |

- "장면 쌍"은 같은 지시문에 대해, 작업 관련 요인 하나만 다르고 정답이 서로 다른 두 배치다 (Part 5.2).

### 4.2 사용자가 제시한 가설 후보와의 대응

| 사용자 후보 | 처리 | 이유 |
|---|---|---|
| 명시적 객체 지시 없이도 목적지 조건을 도출하는가 | H1 | 필요한 전제 능력이다. 그러나 이것만으로는 "LLM이 물류 상식을 안다"는 결과에 그친다 |
| 같은 환경에서 작업 목적이 바뀌면 목적지가 바뀌는가 | 실험 A로 측정. H0의 부 지표 | 지시문만 보고도(영상 없이) 일부 맞힐 수 있어, 단독으로는 장면 근거 사용을 입증하지 못한다 |
| 같은 명령에서 환경이 바뀌면 목적지를 다시 고르는가 | **H0** | 조회표와 사전 지식 추측을 구조적으로 배제하는 유일한 검사다 |
| 어떤 시각적 근거를 사용했는가 | H2 | 모델의 설명을 믿지 않고, 근거를 바꾸거나 가렸을 때 답이 바뀌는지로 잰다 |
| 조건 해석과 기하 검증을 분리하면 성능이 좋아지는가 | H0의 비교 구조 (TC-cond vs TC-direct), H3 | 분리의 효과가 곧 H0의 비교다 |

### 4.3 결과별 해석 (test 전에 고정)

| 결과 | 해석 | 논문에서의 주장 |
|---|---|---|
| H0 지지, 오라클 상태에서도 차이 유지 | 조건 도출과 검증의 분리가 과제 수준 목적지 선택에 유효하다 | 주 결과 |
| TC-cond ≈ TC-direct, 둘 다 높음 | 후보 표시만 있으면 VLM이 과제 수준 선택을 직접 한다. 분리는 필요하지 않다 | "VLM의 과제 맥락 이해"는 지지되고, 구조 주장은 기각된다. 더 단순한 시스템을 권한다 |
| 과제 쌍(실험 A)은 높고 장면 쌍(실험 B)은 낮음 | 지시문에는 반응하지만 장면 상태를 따라가지 못한다. 사전 지식에 의존한다 | 원인을 오라클 상태 조건으로 가른다 |
| 오라클 상태를 주면 장면 쌍이 회복 | 병목은 추론이 아니라 상태 인식(소형 물체)이다. EXP111·EXP112와 같은 결론이다 | 주장을 "조건 도출은 되고, 상태 인식이 한계"로 줄인다 |
| 오라클 조건을 주면 회복 | 병목은 조건 도출이다. 4B 모델의 추론 한계일 수 있다 | 사전 등록한 대체 모델 부 조건(Part 6)을 본다 |
| 미등록 과제에서도 TC-rule ≥ TC-cond | 이 현장에서는 VLM의 조건 도출이 필요하지 않다 | 정직한 부정 결과로 보고한다 |

### 5.6 정답 정의

**정답은 모델 출력이 아니라, 사람이 미리 쓴 두 표에서 나온다.**

1. **과제 정의표** (촬영 전). 과제마다 5.1의 조건을 적는다. 사용자가 쓰고 팀원이 독립적으로 검토한다. 해시를 기록한다.
2. **배치 상태표** (촬영 직후, 모델 실행 전). 사람이 눈으로 보고 적는다. 기존 `annotations_relations/<layout>.json` 형식에 두 항목만 더한다.
   - 기존: 블록 위치(팔레트 위 / 가까운 바닥 / 먼 바닥 / 없음), 팔레트와 기준 물체 쌍의 "옆 / 옆 아님 / 애매"
   - 추가: `truck_cargo` (있음 / 없음), `charge_pad` (비움 / 점유한 물체)
3. **정답 계산**. 과제 정의표의 조건을 상태표에 적용해 선택 / 없음 / 모호 / 확인 불가를 낸다. 사람이 전수 확인한다.
4. **애매한 항목**. 상태표에 "애매"가 들어간 조건으로 정답이 갈리는 항목은 주 분석에서 빼고 따로 보고한다. 이 규칙은 촬영 전에 고정한다.

- 순환 평가가 아닌 이유: "옆"은 사람의 판정을 쓰고, J-geo의 픽셀 규칙이나 모델 출력은 정답에 들어가지 않는다. 이는 계획서 v3 §8.6의 원칙과 같다.
- 장소의 의미가 객체 하나의 존재로 정해지지 않게 한 방법: W03, W04, W05, W08, W09는 모두 "객체는 있지만 과제가 성립하지 않는 배치"를 가진다.
- 사람이 보기에도 하나로 정할 수 없는 경우는 그 자체를 "모호" 정답으로 둔다 (W11).
- 2차 주석자: 과제 정의표와 test 상태표는 팀원이 전부 독립적으로 작성하고 일치율을 보고한다. 박스 주석은 일부만 겹쳐 본다.

## Part 6. 모델 선정

**결론: 현재 구성(Qwen3-VL-4B-Instruct + Grounding DINO tiny)을 유지하고, 새 모델을 설치하지 않은 채 시작한다.** 이 연구에서 모델이 맡는 일은 "탐지"에서 "조건 도출과 국소 상태 확인"으로 바뀐다. 현재 모델이 그 일을 얼마나 하는지는 아직 재지 않았다. 그래서 모델을 미리 바꾸지 않고, 병목이 확인되면 한 가지만 바꾸는 조건을 사전에 등록한다.

### 6.1 기능별 적합성

## Part 7. 평가 지표와 비교군

**결론: 주 지표는 장면 쌍 정답률 하나, 안전 지표는 잘못된 목적지 비율 하나다.** 비교군은 세 개와 오라클 진단 두 개로 제한한다.

각 비교가 답하는 질문

| 비교 | 질문 | 가설 |
|---|---|---|
| TC-cond vs TC-direct | 조건 도출과 검증을 분리하면 나아지는가. 같은 모델, 같은 화소 | H0, H3 |
| TC-cond vs TC-rule | 조건을 VLM이 정해야 하는가, 사람이 쓴 표로 충분한가. 상태 확인과 관계 계산은 같다 | H1 (VLM 필요성) |
| 모두 vs TC-blind | 영상을 쓰지 않고 얼마나 맞힐 수 있는가 | H2 |
| TC-cond에서 ①에 영상 추가 | 조건 도출에 영상이 도움이 되는가 | Q6 |
| 오라클 조건 (사람이 쓴 조건을 ① 대신 넣음) | 오류가 조건 도출에서 오는가 | 진단 |
| 오라클 상태 (사람의 상태표를 ③ 대신 넣음) | 오류가 상태 인식에서 오는가 | 진단 |

공정성 규칙

1. 네 방법은 같은 현장 어휘, 같은 현장 규칙, 같은 후보 번호, 같은 보류 선택지(없음, 모호, 확인 불가)를 받는다.
2. TC-direct에는 TC-cond가 ③에서 보는 것과 같은 후보 확대 영상을 한 장으로 모아 함께 준다. 차이가 화소 수가 아니라 구조에서 나오게 하기 위해서다.
3. TC-rule은 TC-cond와 같은 상태 확인 결과와 같은 관계 계산을 쓴다. 규칙표는 dev 과제만 보고 쓰고 동결한다. 표에 없는 과제에는 사전 등록한 대체 규칙을 쓴다: 지시문과 겹치는 어휘의 객체를 고르고, 없으면 보류한다.
4. 평가 정답과 상태표는 어떤 방법에도 넣지 않는다. 사전 지도는 M00 촬영에서 만든다.
5. 오라클 결과는 진단이다. 시스템 성능으로 보고하지 않는다.

### 7.2 지표

| 지표 | 정의 | 역할 |
|---|---|---|
| **장면 쌍 정답률** | (쌍, 지시문)마다 쌍의 두 배치를 모두 맞히면 정답. 정답이 서로 다른 쌍만 센다. NaturalBench의 Q-Acc, 대조 집합(contrast set)의 일관성 점수와 같은 방식이다 | **주 지표** (H0) |
| **잘못된 목적지 비율** | (다른 대상을 고름 + 정답이 없는데 고름) / 전체 항목 | **안전 지표** |
| 작업 의도 해석·조건 생성 정확도 | 조건 집합 완전 일치율: ①의 출력이 과제 정의표와 정확히 같은 지시문의 비율. 조건별 정밀도와 재현율 | H1 |
| 실제 환경 근거와의 일치도 | (가) 조건 검증 정확도: ③의 판정이 사람의 상태표와 같은 비율. (나) 사전 지식 일치 오류 비율: 쌍의 바뀐 배치에서 틀린 답 가운데 기준 배치의 정답을 그대로 낸 비율. (다) 근거 필요성: 근거 영역을 가리면 "확인 불가"로 바뀌고, 무관한 영역을 같은 크기로 가리면 답이 유지되는 비율 | H2 |
| 정답 목적지 선택률 | 답이 있는 항목 중 맞게 고른 비율 | 부 지표 |
| 보류 | 정답이 없는 항목에서 보류한 비율, 답이 있는 항목에서 보류하지 않은 비율 (GRES의 N-acc, T-acc와 같은 방식), 보류 사유 일치율 | H3 |
| 묶음 정답률 | 한 배치에서 같은 단어 묶음의 지시문을 모두 맞힌 비율 (실험 A). NaturalBench의 I-Acc와 같은 방식이다 | 부 지표 |
| 무관 변화 불변률 | 무관한 변화 뒤에도 답이 같은 비율 | 부 지표 |
| 경로 생성 성공률 | 선택된 목적지 중 목표점이 주행 가능 영역 안에 있고 충돌 없는 경로가 있는 비율 | 시스템 연결 확인 |
| 추론 시간 | 지시 한 건의 총 시간, 호출 수, 최대 VRAM | 보고 |

- 항목별 결과는 EXP120의 6분류(올바른 선택, 잘못된 선택, 놓침, 올바른 보류, 정답 없는데 선택, 형식 오류)를 그대로 쓴다.
- 항목 정답률을 보고할 때는 "늘 같은 답" 정책의 점수를 함께 적는다. W04·W05는 대부분의 배치에서 정답이 같기 때문이다.
- 모든 결과를 "지시문에 없는 조건 수"(0, 1, 3)별로도 나눈다.

### 7.3 통계와 판정

- 독립 단위는 쌍이다. 같은 기준 배치에서 나온 배치들은 한 묶음으로 센다. 프레임 3장은 일관성 확인에만 쓴다.
- 주 비교는 하나다: 장면 쌍 정답률에서 TC-cond 대 TC-direct.
  - 쌍 단위 차이에 대한 정확 부호 뒤집기 순열 검정을 쓴다. 비율에는 원래 개수와 Wilson 구간(또는 Beta 사후 구간)을 붙인다.
  - 쌍이 10개 안팎이면 bootstrap 구간은 믿기 어렵다 (Bowyer et al., 2025). EXP110에서 쓴 군집 bootstrap은 군집이 49개였다.
- 표본이 작다는 점을 미리 적는다.
  - test 쌍은 8개(선택 배치를 더하면 10개)다.
  - 정확 부호 검정 기준으로, 두 방법의 결과가 갈린 쌍이 6개 이상이고 모두 같은 방향이어야 양측 p < 0.05다 (6쌍 p = 0.031, 5쌍 p = 0.063).
  - 그래서 판정은 EXP110처럼 지지 / 지지되지 않음 / 확정하지 못함의 세 가지로 한다.
- 부 비교는 Holm 보정을 한다.
- 설계 점검: TC-blind의 장면 쌍 정답률은 0이어야 한다. greedy decoding에서는 영상이 없으면 쌍의 두 배치에 같은 답을 내기 때문이다. 0이 아니면 쌍 설계의 결함으로 기록한다.
- 일관성만 보고하지 않는다. 답이 일관되게 틀릴 수 있으므로, 쌍 지표는 항상 정답 여부와 함께 센다.
- 수치 임계값(예: H3의 놓침 한도)은 dev 결과를 본 뒤, test 전에 고정한다.

### 8.3 dev와 test의 독립, 동결

- XD 배치는 dev 기준 배치에서만, XT 배치는 test 기준 배치에서만 만든다. dev와 test가 섞이지 않는다.
- test는 T와 XT를 한 세션에서 찍고 바로 해시로 봉인한다 (기존 규칙).
- EXP111, EXP112, E3a, 이 실험이 같은 test를 쓴다. 모든 설정을 한꺼번에 동결한 뒤 test를 한 번만 돌린다. 이 점은 기존 감사의 권고와 같다.
- dev에서 정하는 것: 프롬프트, 조건 형식, 상태 질문 문장, TC-rule 규칙표, 수치 임계값.
- test를 본 뒤에는 모델, 프롬프트, 평가 기준을 바꾸지 않는다. 바꾸면 새 판으로 기록하고 사후 분석으로 표기한다.
- test 전용 지시문은 팀원이 쓰고 봉인한다 (5.1).
- EXP110의 P01–P10은 다시 쓰지 않는다.

### 8.4 장면 수보다 중요한 독립적인 환경 변화

| 순위 | 변화 | 이유 |
|---|---|---|
| 1 | 작업 관련 상태의 뒤집힘 (트럭 상자, 팔레트 적재, 충전 패드) | 쌍의 수가 곧 주 지표의 표본 수다 |
| 2 | 정답 위치의 분산 | 같은 과제의 정답이 여러 위치에 나와야 위치 암기와 구분된다 |
| 3 | 같은 단어, 다른 목적 | 지시문만 바꾸므로 사진 없이 늘릴 수 있다 |
| 4 | 무관한 변화 | 답이 유지되어야 하는 대조다 |
| 5 | 답할 수 없는 유형의 다양성 (없음, 모호, 확인 불가) | 보류 능력은 유형마다 다르게 나타난다 |
| 6 | 처음 보는 과제와 표현 | 규칙표와 VLM을 가르는 유일한 축이다 |

- 덜 중요한 것: 배치당 프레임 수, 같은 배치의 반복 촬영, 고정물 종류 수.
