# 독립 시험: 예전 실행 vs 새 버전 (새 사진) — 사전 등록 2026-11-22

- 상태
  - 시험: **NOT_STARTED**. 새 사진을 기다린다.
  - 도구: **TESTING**. 오프라인 검사 6/6 통과(아래). GPU 실행은 아직 하지 않았다.
- 규칙 원본은 `config/holdout.yaml`이다. 이 문서는 그 설명이다. 정답을 확정한 뒤에는 둘 다 바꾸지 않는다.
- 다른 실험 폴더는 읽기만 한다. 쓰는 파일은 모두 이 폴더 안에 있다.

## 왜 하는가

2차 공유 사진 15장에서는 새 버전(맥락 정책) 결과가 더 좋았다.

| 15장 결과 | 예전 실행 | 새 버전 |
|---|---|---|
| A 잘못 확정 | 1 | 0 |
| B 맞음 | 11 | 12 |
| 경로 그림까지 | 9 | 11 |

하지만 새 버전 규칙은 이 15장에서 본 실패를 보고 만들었다. 작업대 물건, 꼬깔, 놓친 팔레트, Z07이 그 실패다. 그래서 15장은 새 버전에게 독립 시험이 아니다.

두 버전 모두 본 적 없는 새 사진에서 미리 정한 규칙으로 한 번만 비교한다. 새 버전이 이기면 본문 기준을 새 버전으로 바꾼다.

## 비교 대상 (코드·설정을 바꾸지 않고 부른다)

| | 예전 실행 | 새 버전 |
|---|---|---|
| 폴더 | `nl_to_route_20261122` | `context_policy_20261122` |
| 부르는 방법 | `nl_to_path.main()` 그대로 | `extract.main()`, `policy.run_set`·`draw_photo`, `nl_to_path.run_one` 그대로 |
| 실행 중에 바꾸는 값 | `CFG.photo_set.dir` 하나. `--all` 사진 목록에만 쓰인다 | 아래 세 가지 |
| 기준값 | 설정 그대로 (0.88, 0.02, 20 cm 등) | 개발 8장에서 정한 `data/dev/calibration.json` 그대로 |
| 지시 | I1 "빨간 큐브를 비어 있는 팔레트로 옮겨줘." | 같음 |

새 버전에서 바꾸는 값 세 가지 (`new_system.py`):
1. `common.C['photo_sets']['holdout']`: 새 사진 폴더와 2차 사진 자세
2. `extract.HERE`, `policy.HERE`: 출력 위치를 이 폴더로
3. `policy.gt_for`: 이 시험의 정답. policy가 남기는 참고 등급에만 쓰이고 결정에는 쓰이지 않는다. 채점은 `score.py`가 한다.

## 실행 전에 고정하는 것 (`FREEZE.json`)

- 두 버전과 그 아래에서 불리는 코드·설정의 sha256: 혼합 파이프라인, 멀티모델 코드, v0.2 모델 작업 코드, 정답 박스 출처 파일
- 개발 사진 8장(예시 이미지 출처), 카메라 자세 파일, 이 시험의 코드와 설정
- 모델 4개의 Hugging Face 리비전: Qwen3-VL-4B, Grounding DINO tiny, SigLIP2 base, SigLIP2 so400m
- 실행 직전에 다시 대조한다. 하나라도 다르면 실행하지 않는다.
- 정답을 확정하거나 실행 폴더가 생긴 뒤에는 `freeze.py --write`가 거부된다.

## 사진 조건 (`run_holdout.py`가 확인)

- 2차 공유 사진과 **같은 카메라, 같은 자리, 같은 도구로 편 사진**(`*_view.png`, 1920×1080)이어야 한다. 기준 사진과 배경 특징점이 3 px 넘게 어긋나면 거부한다.
  - 2차 사진은 alpha 0 newK로 편 것으로 추정했다(INFERRED). 다른 방식으로 펴면 어긋남 검사에서 걸린다.
- **로봇은 2차 사진과 같은 출발 자리**에 둔다. ArUco id 0 꼭짓점이 3 px 안이어야 한다. 두 버전 모두 출발 자리를 설정값으로 쓰기 때문이다.
- 2차 사진 15장과 같은 파일은 거부한다.
- 가능하면 펴기 전 원본 사진도 함께 받아 둔다. 실행에는 쓰지 않는다.

### 촬영 목록

| 묶음 | 태그 | 장수 | 배치 | 정답 |
|---|---|---|---|---|

| 보고만 | E2 | 1 | 큐브 2개 | 어느 쪽이든 맞음 |

장수는 목표다. 정답 도구에서 사진마다 태그를 붙이고, 실제 장수를 결과에 그대로 적는다.

## 정답 (실행 전에 사람이 확정)

1. 새 사진을 `data/photos/`에 넣는다.
2. `gt_tool.py`를 실행하고 `http://127.0.0.1:8766`을 연다.
3. 사진마다 다음을 한다.
   - 큐브 윗면 가운데와 빈 팔레트 윗면 가운데를 모두 클릭한다.
   - 없으면 비워 둔다.
   - 시나리오 태그를 고른다.
   - "검토 완료"를 표시한다.
4. 모든 사진이 끝나면 이름을 적고 "정답 확정"을 누른다.
   - 그 뒤에는 정답을 고칠 수 없다.
   - 실행은 확정된 정답만 받는다.
   - 채점 때 정답 파일 sha256이 실행 때와 다르면 채점을 거부한다.

## 채점과 판정 (`score.py`, 두 버전에 같은 규칙)

등급:

| 정답 | 결과 | 등급 |
|---|---|---|
| 물체가 있음 | 고른 박스 중심이 정답 점에서 20 px 안 | 맞음 |
| 물체가 있음 | 20 px 밖을 고름 | 틀리게 확정 |
| 물체가 있음 | 고르지 않음 | 놓침(보류) |
| 물체가 없음 | 고르지 않음 | 맞는 보류 |
| 물체가 없음 | 무언가 고름 | 틀리게 확정 |

판정 규칙 (판정용 묶음 P1~P4만 쓴다):
- 새 버전의 잘못 확정(A+B)이 예전 이하이고, 맞음(맞는 보류 포함)이 예전 이상이면 → 본문 기준을 새 버전으로 바꾼다. 예전 실행은 이전 결과로 함께 적는다.
- 아니면 → 본문은 예전 실행을 유지하고, 새 버전은 별첨에 둔다.
- 경로 그림까지 몇 장인지는 보조 지표다. 판정에 쓰지 않는다.
- 사진이 적어 통계적 유의성은 주장하지 않는다. 개수만 보고한다.

## 순서

```bash
cd /home/binci/vlm_ws/holdout_test_20261122
PY=/home/binci/miniconda3/envs/stnav_gui/bin/python
$PY -B freeze.py --check                 # 고정 목록과 같은지
$PY -B gt_tool.py                        # 정답 찍기 -> 확정
$PY -B run_holdout.py --check-only       # 실행 전 확인만
$PY -B run_holdout.py                    # 한 번만 실행 (GPU, 사진 1장에 약 100 s) -> results/run_<시각>/ + score.md
```

- 실행 폴더에 남는 것:
  - `manifest.json`: 시작 시각, 고정 목록·정답 sha256, 사진별 확인 결과, 설정, GPU
  - 예전 버전 결과 `old/`
  - 새 버전 결과 `new/`: 특징, `decisions.json`, 그림, 경로
  - 로그 두 개, `score.json`, `score.md`
- 끝난 실행이 있으면 다시 실행하지 않는다.
- 중간에 멈춘 실행이 있을 때만 `--retry-reason`으로 다시 할 수 있다. 이유는 manifest에 남는다.

## 한계

- 정답은 사람이 찍는다. 15장의 정답은 AI 판독이었다.
- 지시는 I1 하나다. Qwen 글자 단계의 가치는 이 시험으로 보이지 않는다.
- 로봇 출발 자리와 카메라는 2차 사진과 같아야 한다. 다르면 두 버전 모두 자세를 다시 구해야 해서 이 시험 범위 밖이다.
- 그리퍼 도달·실제 주행은 다루지 않는다. "경로 그림까지"는 그림이 나왔다는 뜻이고 주행 가능을 뜻하지 않는다.
