- 표기: `CONFIRMED` 저장된 파일·코드로 직접 확인 / `INFERRED` 확인한 사실에서 이어지는 해석 / `UNKNOWN` 확인하지 못함

## 0. 먼저 읽을 결론

1. **V1은 세 저장 사례를 모두 막았지만, 이유가 서로 다른 세 가지인데 V1에는 구분이 없었다.** V2는 같은 제안을 세 가지로 갈랐다: DEV_REF는 *근거 물체가 있으나 관계가 성립하지 않음*, E1은 *의미는 타당하나 배치가 검증되지 않음*, REF_P01은 *시각적 근거가 확인되지 않음*.
2. **E1에서 V1은 의미가 맞는 제안을 `SEMANTIC_NOT_VERIFIED`로 기록했다.** 영역이 넓다(트럭의 4.08배)는 이유였다. V2는 이를 `SEMANTICALLY_SUPPORTED_PLACEMENT_UNVERIFIED`로 분리해, 의미 후보는 보존하고 계획만 중단한다. 반대로 V1의 한계를 6배로 완화하면 같은 거친 영역이 지도가 정합될 때 계획으로 넘어간다. V2는 크기를 어느 쪽으로도 쓰지 않는다.
3. **V1이 틀릴 수 있는 방향이 합성 시나리오로 확인됐다.** 트럭이 아닌 올바른 운반 수단을 거부하고(S6), 지시문의 목적을 보지 않고 통과시키고(S7, S9), 검증되지 않은 물리적 근거를 무시하고 통과시킨다(S8). V2는 각각 다르게 처리한다.
4. **V2는 어떤 저장 사례도 계획 단계로 넘기지 않았다.** 목표가 통과율이 아니므로 정상이다. 세 사례 모두 배치 근거(검증된 localization)가 없다.
5. 기존 코드와 저장 결과는 수정하지 않았다(§9).

## 2. 새 검증 알고리즘(V2)의 구조

`verifier2.py` (순수 함수). 입력: 후보 영역들, 관찰(탐지 결과, 어떤 클래스를 실제로 찾아봤는지, 검증된 localization, 지도 정합 상태), 지시문. 출력: 후보별 축 A–E 판정과 최종 상태.

```text
A 근거      observed_evidence 문장 → 클래스 사전에 맞춤 → 탐지기 관찰에서 조회
              (VERIFIED_PRESENT / NOT_FOUND(찾아봤으나 없음) / NOT_RUN(관찰 없음) / UNVERIFIABLE(탐지기 없음) / NOT_EVIDENCE(옮길 물체))
B 관계      인스턴스마다 영역과의 관계: 안에 있는 비율 ≥ v0.2 기준 0.5, 또는 간격 ≤ band_depth(물체)  (v0.2 설정에서 읽음)
C 목적      지시문 → 목적(출하 등) → 필요한 능력.  검증됐고 관계가 성립하며 "인용된" 물체의 능력이 이를 충족하면 SUPPORTED
의미 판정    A+B+C → SEMANTICALLY_SUPPORTED / EVIDENCE_NOT_ESTABLISHED / EVIDENCE_RELATION_INCONSISTENT / PURPOSE_FIT_UNDETERMINED
D 배치      검증된 localization이 있고 충돌이 없으면 ESTABLISHED.  영역 크기는 쓰지 않고 보고만 한다
E 인터페이스  장애물 모델이 이 목적지를 표현하는가 (모델링되지 않은 물리적 근거 주장, 관찰되지 않은 장애물 클래스)
최종         의미 판정이 통과해야 D, E를 본다 → …_PLACEMENT_UNVERIFIED / …_PLANNER_UNSUPPORTED / …_READY_FOR_PLANNING
전제조건     지도 정합, 큐브 탐지 등은 별도 필드 (hand_over_to_planner = READY 이면서 전제조건이 막히지 않음)
```

핵심 설계 결정:
- **VLM의 설명은 근거가 아니다.** `function_name`, `confidence`, `inference`는 기록만 하고 판정에 쓰지 않는다(테스트: 설명을 과장해도 판정이 같다). 추론 문장에만 나온 물체는 근거로 세지 않고 별도로 기록한다. VLM이 스스로 "(assumed)"라고 쓴 근거는 `hedged`로 표시한다.
- **특정 시설을 요구하지 않는다.** 클래스 → 능력 표(`carrier_vehicle` 등)와 목적 → 필요한 능력 표가 데이터로 있다. 능력을 가진 어떤 클래스든 인정하고(합성 S6), 사전에 없는 시설은 **거부가 아니라 보류**다(S10). 이 두 표는 사람이 쓴 사전 지식(`manual_prior`)이며 `config.yaml`에 명시했다.
- **크기로 판정하지 않는다.** 배치는 검증된 localization(근거 문구를 grounding한 박스가 제안 안에 있고 검증된 근거 물체와 맞닿음)으로만 성립한다. V1의 2.5배는 `legacy_v1_size_gate`로 옆에 보고만 한다.
- **계획기 지원을 의미 검증과 분리한다.** v0.2의 기본 목적지 단계는 트럭에 앵커된 `loading_area`만 다루지만(`agent/task_parser`, `semantics/region_grounding`), 배치·접근·경로 단계는 임의의 영역 다각형을 받는다. V2는 목적지를 트럭 유형으로 변환하지 않는다. 대신 계획기의 장애물 모델(탐지된 객체와 지도만 안다)이 이 목적지를 표현할 수 있는지를 따로 본다.
- **VLM의 선택을 바꾸지 않는다.** 후보가 여럿이면 각각 판정하고 선택하지 않는다(S4).

## 3. 기존 방식과 새 방식의 차이

| 관점 | V1 | V2 |
|---|---|---|
| 기준 객체 | 트럭 필수 | 능력 표에 있는 어떤 클래스든 (트럭 고정 없음) |
| 지시문 | 사용 안 함 | 목적을 지시문에서 읽어 필요한 능력을 정함 |
| 근거 | 트럭 존재 확인 + 나머지는 목록 | 근거마다 `VERIFIED/NOT_FOUND/NOT_RUN/UNVERIFIABLE` + 영역과의 관계 |
| 검증 불가 근거 | 무시 | 근거로 세지 않고, 물리적 물체면 장애물 모델 공백으로 기록 |
| 크기 | 의미 판정을 막는 게이트 | 판정에 쓰지 않음, 보고만 |
| 같은 모델의 판정기 | 필수 게이트 | 근거로 쓰지 않음 |
| 의미/배치/계획 지원 | 한 상태 | 별도 축, 별도 상태 |
| 후보 여러 개 | 선택된 하나만 | 후보별 판정, 선택은 하지 않음 |
| 지원하지 않는 유형 | 트럭이 아니면 실패 | 의미 판정은 유지, 계획기 지원 여부만 따로 표시 |

## 5. 각 후보의 채택·보류 사유

**DEV_REF — `EVIDENCE_RELATION_INCONSISTENT` (보류)**
- 근거 `dump truck`: 트럭은 **실제로 있다**(`VERIFIED_PRESENT`). 그러나 영역과의 관계가 성립하지 않는다: 영역 안 비율 0.0, 간격 **227.7 px > 인접 허용 119.5 px**. V1도 같은 사실로 막았지만(V3) "트럭이 있으니 근거는 확인됨"(V2 VERIFIED)과 "관계 실패"를 한 상태로 섞었다.
- 근거 `pallets with containers`, `orange cones`: 이 사례 기록에는 해당 클래스의 관찰이 없어 `NOT_RUN` (거부가 아님).
- 배치: 검증된 localization 없음 → `NOT_ESTABLISHED`. 독립 지도 검사에서 영역의 99.8%가 로봇 주행 구역(DRAFT 지도) 안이다.
- 해석(`INFERRED`): VLM은 컨테이너 적치 줄을 하역 구역으로 읽었고, 멀리 있는 트럭을 근거로 끌어왔다.

**E1 — `SEMANTICALLY_SUPPORTED_PLACEMENT_UNVERIFIED` (의미 후보 보존, 계획 중단)**
- 근거 `truck`: `VERIFIED_PRESENT`, 영역 안 비율 1.0, `RELATION_HOLDS`. 근거 `cones`: 6개 모두 검증, 6개 모두 영역 안 (같은 이미지·같은 VLM 응답의 변형 실행 기록을 합쳐 사용, 응답 원문 동일을 확인). 근거 `barriers`: 클래스 사전에 없는 물리적 물체 → `UNVERIFIABLE`.
- 목적: 지시문의 "출하" → 필요한 능력 `carrier_vehicle`. 검증된 트럭이 이 능력을 갖고 관계가 성립 → `SUPPORTED`. 이 결론은 VLM의 설명이 아니라 **검증된 능력 근거**에 기댄다. (한계: 트럭이 근처에 있다는 것이 그곳이 지정된 출하 장소라는 증명은 아니다. 그럴듯함의 근거이고 확정이 아니다.)
- 배치: VLM 자신의 근거 문구를 grounding한 12개 박스가 모두 제안 밖이라 localization이 없다 → `NOT_ESTABLISHED`. 크기는 쓰지 않았다(영역 이미지 대비 7.8%, 레거시 비율 4.5배는 참고).
- 계획 인터페이스: `barriers`가 모델링되지 않은 물리적 주장이라 장애물 범위 `INCOMPLETE`. 전제조건: 지도 `MISALIGNED`, 큐브 `TARGET_NOT_FOUND`.

**REF_P01 — `EVIDENCE_NOT_ESTABLISHED` (보류)**
- 근거 `lightning bolt symbol`은 바닥 표시(탐지기 없음 → `UNVERIFIABLE`), `whiteboard nearby`는 사전에 없는 물체 → `UNVERIFIABLE`, `red cube marker (assumed)`는 옮길 물체이며 VLM 스스로 추정이라 표시 → `NOT_EVIDENCE`. **확인된 근거가 하나도 없다.**
- 이것은 "충전 구역이 틀렸다"는 판정이 아니다. 목적에 필요한 능력을 가진 검증된 근거가 없다는 뜻이다. 목적지가 무엇인지는 이 검증기가 정하지 않는다.

## 6. 의미적 타당성과 배치 가능성을 분리했는가 — 예

- 의미 판정(`semantic_verdict`)은 축 A+B+C만으로 정해지고, 영역 크기와 배치 정보는 입력되지 않는다 (테스트: 영역을 키워도 의미 판정과 배치 상태가 그대로이고, `region_size_info`만 달라진다).
- 배치는 검증된 localization으로만 성립한다 (테스트: 제안 밖의 박스나 인정되지 않은 출처의 박스는 거부).
- E1이 그 증거다: V1은 두 개념을 섞어 의미 미검증으로 기록했고, V2는 `SEMANTICALLY_SUPPORTED`와 `PLACEMENT_UNVERIFIED`로 나눈다. 배치를 검증할 수 없으므로 의미 후보만 보존하고 계획은 중단한다.
- 계획기 지원 여부(축 E)도 의미 판정과 별도 필드다. 목적지를 트럭 유형으로 바꾸지 않았다.

## 8. 발견된 한계

1. **능력 표와 목적 표는 사람이 쓴 사전 지식이다.** `truck → carrier_vehicle`, `출하 → carrier_vehicle`가 사실상 V1의 트럭 선호를 능력 단위로 옮긴 것일 수 있다. 달라진 점은 특정 클래스 이름이 아니라 능력으로 요구한다는 것, 표에 없는 시설은 거부가 아닌 보류라는 것이다. 표의 적절성은 사용자가 검토해야 한다.
2. **키워드 기반 목적 추출이다.** 목적 세 개(출하, 하역, 충전)만 안다. 모르는 지시문은 전부 `PURPOSE_FIT_UNDETERMINED`가 된다. 안전한 방향이지만 자율성은 줄어든다.
3. **탐지기 범위가 좁다.** 이번 오프라인 기록에서는 DEV_REF와 REF_P01의 콘·팔레트·컨테이너가 `NOT_RUN`이다(관찰 자체가 없음). 이것이 계획 인터페이스의 "장애물 범위 INCOMPLETE" 표시에 섞여 있다(증거가 아니라 수집 공백 때문). 온라인 수집 단계를 돌리면 달라진다.
4. **관찰의 독립성이 완전하지 않다.** v0.2의 탐지 검증에는 같은 계열의 Qwen 크롭 확인이 들어 있다. 이 설계는 VLM의 설명을 쓰지 않을 뿐, 모든 관찰이 VLM 계열과 무관한 것은 아니다.
5. **관계 규칙이 거칠다.** "안에 있거나 band_depth 이내"는 트럭이 영역을 향하는지, 그 영역이 실제 상차 위치인지 모른다. v0.2의 규칙을 그대로 따른 것이다.
6. **배치를 성립시킬 수단이 하나뿐이다.** 검증된 localization(근거 grounding)이 세 사례 모두에서 없었다. 바닥 표시선을 직접 찾는 수단은 없다. 그래서 실제 기록 중 **READY까지 간 것이 없고**, 연결(통과) 경로는 합성 입력으로만 시험했다.
7. **정답이 없다.** "false accept/reject"는 이유가 있는 후보 표기이지 정확도가 아니다. 실제 사례는 3건이다.
8. **보수적 표시**: `barriers`(VLM이 콘을 가리킨 말일 수 있음)와 `whiteboard nearby`("근처"는 영역 밖일 수 있음)도 모델링되지 않은 물리적 주장으로 센다.
9. **지도 충돌 검사는 V1의 임계값(5%)을 그대로 쓴다.** REF_P01의 7.1%는 경계값에 가깝다. 의미 판정에는 영향이 없다.
10. V1 재생은 게이트를 다시 구현한 것이다. 저장된 4건과의 일치로 확인했지만 새 입력에서의 일치까지 보장하지는 않는다.
11. V2는 `IntegrationRun`에 연결하지 않았다. 오프라인 검증기일 뿐이고 실제 모델 실행에서의 동작은 확인하지 않았다.

## 10. 다음 단계에서 해결해야 하는 문제

1. **온라인 근거 수집 단계**: 클래스 사전의 DINO 검증 클래스(콘, 팔레트, 컨테이너)를 세 사례에서 실제로 수집해, DEV_REF의 "컨테이너 적치 줄"이 보관 능력의 근거를 갖는지(`goods_staging`)와 계획 인터페이스 판정의 수집 공백을 없앤다. 새 모델 호출이 필요하다.
2. **배치 localization 수단**: 바닥 표시선(점선 구획)을 검증 가능한 형태로 찾는 방법. 지금은 VLM 자신의 근거 문구 grounding뿐이고 E1에서 실패했다. 사람이 쓴 질의("parking space of the truck")를 C1급 사전 정보로 명시하고 쓸지, 표시선을 Python이 직접 찾을지는 사용자 결정이 필요하다.
3. **능력 표와 목적 표의 검토와 확장**: 어떤 시설이 어떤 목적을 충족하는지는 사용자의 도메인 지식이다. 출하 목적에 `outbound_handoff` 같은 비차량 능력을 넣으려면 해당 탐지기가 먼저 필요하다.
4. **정답 영역과 수용 가능한 후보 집합을 사람이 사전에 작성**해야 V1/V2의 false accept/reject를 정량화할 수 있다.
5. **V2를 통합 실행에 연결**(선택 가능한 검증기로)하고 실제 모델 실행에서 확인. E1은 지도 정합과 큐브 탐지가 따로 해결되어야 한다.
6. **VLM 제안의 안정성**: 같은 배치에서 답이 갈린다. 여러 번 샘플링한 제안을 V2가 각각 판정해 일치하는 후보를 보는 방법.
7. **관찰의 독립성 보강**: Qwen 크롭 확인을 쓰지 않는 근거(예: 색, 형태 기반 확인)나 별도 검증 모델은 이번 범위가 아니다.
