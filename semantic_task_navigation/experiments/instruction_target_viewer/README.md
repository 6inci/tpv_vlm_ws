# 작업지시 대상 시각화 (instruction_target_viewer)

사진 한 장을 고르고 자연어 작업지시를 입력해 실행하면, 기존 VLM 파이프라인이 **옮길 물체 A**와 **놓을 곳 B**를 추론해 사진 위에 표시합니다. 프로그램을 다시 시작하지 않고 같은 사진에서 지시를 바꿔 계속 실행할 수 있고, 이전 실행과 나란히 비교할 수 있습니다.

## 실행

```bash
cd /home/binci/vlm_ws/semantic_task_navigation
/home/binci/miniconda3/envs/stnav_gui/bin/python experiments/instruction_target_viewer/viewer_app.py
```

창 없이 여러 지시를 한 세션에서 실행할 수도 있습니다.

```bash
/home/binci/miniconda3/envs/stnav_gui/bin/python experiments/instruction_target_viewer/viewer_app.py --headless --photo U25070552 \
  --instruction "컨베이어 옆의 빨간 큐브를 하역장으로 옮겨줘." --instruction "트럭 주변의 상자를 컨베이어 옆으로 가져와."
```

- 모델은 기존 v0.2 작업 프로세스(`qwen_vl` 환경, Qwen3-VL-4B와 Grounding DINO)를 그대로 씁니다. 12 GB GPU라서 두 모델을 번갈아 올립니다.
- 다른 모델 프로그램이 GPU를 쓰는 중이면 실행하지 마세요.

## 화면

| 위치 | 내용 |
|---|---|
| 왼쪽 | 사진 목록, 작업지시 입력, 규칙(R1 작업장 규칙 / R0 없음), 실행·중지, 진행 단계, GPU 사용량, 저장 폴더 |
| 가운데 | 결과 사진(설명은 아래 표) |
| 오른쪽 위 · 판단 결과 | 입력, 해석, 선택된 A·B, 선택 근거, 판단 상태 |
| 오른쪽 위 · 단계별 상태 | 해석 → 탐지 → 기준 시설 → 후보 → Qwen 역할 판단 → 접근성 → 결정. 처음 실패한 단계가 보입니다 |
| 오른쪽 위 · 후보 판단 | 후보마다 Qwen이 본 것, 역할, 적재 상태, 접근 가능 여부. Qwen에 실제로 들어간 번호 이미지도 볼 수 있습니다 |
| 오른쪽 아래 · 실행 기록 | 이 세션의 모든 실행. 한 줄을 고르면 그 결과를, Ctrl+클릭으로 두 줄을 고르면 위아래로 비교합니다 |

결과 사진의 표시는 다음과 같습니다.

| 표시 | 뜻 |
|---|---|
| 빨간 실선 | A 출발 대상 |
| 파란 실선 | B 목적 대상 |
| 파란 반투명 칠 | B가 구역(`GOAL_REGION`) |
| 초록 화살표 | A → B |
| × 표시 | 로봇 정차 위치(접근 자세) |
| 점선 사각형 | A·B 탐색 영역 |
| 빨강·파랑 점선 + `A?` `B?` | 동률이라 판단 보류한 후보 |
| 회색 점선 | Qwen은 받아들였지만 로봇이 닿지 못하는 후보 |
| "판단한 후보 모두 표시" | Qwen이 판단한 모든 후보와 역할 |

## 한 번의 실행에서 하는 일

1. **해석 (Qwen)**: 옮길 물체, 출발 기준 시설과 관계, 목적지 의미, 목적지 기준 시설과 관계를 뽑습니다. `task_context_v1` 프롬프트를 씁니다.
2. **탐지**: 사진마다 한 번만 하고 다시 씁니다.
   - E1: 저장된 E1 기준 시설과 후보를 씁니다.
   - 다른 사진: 이 세션에서 DINO와 Qwen 크롭 확인을 한 번 실행합니다.
   - 새 지시에 처음 나오는 물체 이름만 DINO로 추가 탐지합니다.
3. **기준 시설 → 탐색 영역**: task_context 규칙(`on` = 내부, `next_to`/`near`/`from` = 주변)을 따릅니다.
4. **A 판단 (Qwen)**: 영역 안 후보에 번호를 붙여 묻습니다. 정확히 하나면 `SELECTED`, 여럿이면 `AMBIGUOUS`이며 첫 번호를 고르지 않습니다.
5. **B 판단 (Qwen)**: 영역 안 후보에서 옮길 물체를 뺀 뒤 묻습니다. 접근성은 기존 Python 규칙(주행 구역에서 5 cm 이내, 로봇 출발점에서 접근 자세 도달)으로 확인하고, task_context의 Tier1/Tier2 정책으로 결정합니다.
6. **결과 저장**과 그림 그리기.

해석과 역할 판단은 지시마다 새로 실행합니다. 이전 지시의 A·B는 다시 쓰지 않습니다.

## 표시 라벨

| 라벨 | 뜻 |
|---|---|
| `SELECTED` | 하나로 결정됨 |
| `AMBIGUOUS` | 동률이라 판단 보류 |
| `NOT_FOUND` | 해당 후보 없음 |
| `NOT_ACCESSIBLE` | 적합한 후보가 있지만 로봇이 닿지 못함 |
| `NO_REFERENCE` | 지시에 나온 기준 시설을 사진에서 찾지 못함 |
| `TOO_MANY_CANDIDATES` | Qwen 호출 3회를 넘는 후보 수 |
| `OBJECT` / `GOAL_REGION` | B가 물체인지 구역인지. 탐지 문구·Qwen 묘사의 구역 단어, 또는 사진 면적 3 % 이상으로 정하는 표시 규칙이며 검증되지 않았습니다 |
| `VLM_SUITABLE_EMPTY` | Qwen이 "적합하고 비어 있음"이라고 본 물체 |
| `PLACEMENT_UNVERIFIED` | 배치면 여부 미확인 |
| `*_ACCESSIBILITY_NOT_CHECKED` | 바닥 변환이 맞지 않거나 로봇을 찾지 못해 접근성을 확인하지 않은 결정 |

`VLM_SUITABLE_EMPTY`와 `PLACEMENT_UNVERIFIED` 어느 쪽도 물리적 배치(면 크기, 그리퍼 도달)를 확인했다는 뜻은 아닙니다.

## task_context와 다른 점 (이 프로그램에서 추가한 규칙)

- **지시에 기준 시설이 전혀 없을 때** (예: "빨간 큐브를 …"): task_context는 `NO_REFERENCE`로 끝냈지만, 여기서는 사진 전체를 탐색 영역으로 씁니다(`WHOLE_IMAGE`).
  - 출발 쪽은 물체 이름이 들어간 탐지 후보만 씁니다. 빨간 큐브는 저장된 큐브 후보를 그대로 씁니다.
  - 기준 시설을 말했는데 찾지 못한 경우는 여전히 `NO_REFERENCE`입니다.
- **후보가 20개를 넘을 때**: 자르지 않고 번호 이미지를 나눠 여러 번 묻습니다. 한 이미지라도 응답이 잘못되면 판단 보류입니다.

## 작업장 규칙: 요청하신 조건과 기존 R1의 차이 (덮어쓰지 않음)

R1(`task_context_2d_navigation/config.yaml`의 `rules_R1`)을 그대로 씁니다. 요청하신 조건과 비교하면 다음과 같습니다.

| 요청 조건 | 기존 R1 / 프롬프트 | 차이 |
|---|---|---|
| 노란색 영역은 주행 가능 영역 | "노란 외곽선 안의 넓은 검은 바닥은 로봇 주행 구역", "노란 테두리 안의 화물 적치·자재 보관 구역에는 본체가 들어가지 않고 접근만" | R1은 노란 테두리 구역 중 일부를 진입 불가로 나눕니다. "노란색 = 주행 가능"과 부분적으로 충돌합니다 |
| 초록 보행 동선은 주행·물품 배치에 쓰지 않음 | "보행자 통로이며 로봇 본체가 들어갈 수 없다" | 배치 금지는 R1에 명시돼 있지 않습니다. 접근성 규칙으로만 막힙니다 |
| 트럭 주변 주의 | "트럭과 흰색 점선 구획은 트럭 하역장" | "주의"에 해당하는 규칙은 없습니다 |
| 지지면, 여유 공간, 적재 상태 고려 | 목적지 프롬프트가 적재 상태와 "올려놓을 수 있는 형태"를 묻습니다 | 여유 공간은 묻지 않습니다 |
| 공간 관계는 실제 이미지에서 확인 | 관계 영역은 사진에서 찾은 기준 시설 박스로 계산합니다 | 같습니다 |

규칙을 바꾸려면 R1 사본을 새 이름으로 만들어 비교 실험으로 진행하는 것을 권합니다(기존 R1 보존).

## 저장

프로그램을 켤 때마다 새 세션 폴더가 생깁니다. 기존 결과는 덮어쓰지 않습니다.

```
results/<날짜_시각>_session/
  session.json                 실행 목록 요약, v0.2 코드 해시가 그대로인지
  photos/<사진ID>.json         사진별 기준 시설, 탐지 후보(ID와 박스), 정렬 상태, 탐지 모델 호출
  runs/run_<번호>_<사진ID>/
    run.json                   전체 기록 (아래 목록)
    overlay.png                A·B 결과 그림
    overlay_candidates.png     후보까지 표시한 그림
    inputs/*.png               Qwen에 넣은 번호 이미지
    qwen/*.txt                 Qwen 원문 응답, qwen/*_prompt.txt = 프롬프트 원문
    model_calls.json           모델 호출 기록 (모델, 커밋, 프롬프트 해시, 지연 시간)
  worker_logs/
```

`run.json`에 들어가는 것:
- 사진 경로와 해시, 작업지시, 규칙
- 프롬프트 ID, 모델 호출 여부(`model_called: true`)
- 해석 결과
- 기준 시설과 탐색 영역
- 후보 ID와 박스
- Qwen 판단
- 접근성
- A·B 결정과 근거
- 단계별 상태와 최초 실패 단계
- `handoff`: 나중에 기존 지도와 경로계획에 넘길 수 있는 A·B 정보입니다.
  - ID
  - 사진 px 박스
  - 바닥 cm 다각형 (임시 E1 변환)
  - 접근 자세

## 한계

- 바닥 좌표와 접근성은 E1 매트 이음매로 만든 **임시 변환**(PROVISIONAL, RMS 3.57 cm)과 **DRAFT 지도**에 의존합니다. E1과 카메라가 정렬된 사진에서만 의미가 있습니다. 세션 사진 8장은 모두 정렬되어 있습니다.
- 그리퍼 도달 거리와 배치면의 물리적 크기는 확인하지 않습니다.
- 이미지 위 라벨은 영어입니다(OpenCV). 한국어 설명은 오른쪽 패널에 있습니다.
- Qwen3-VL-4B의 알려진 인식 오류(작은 팔레트 오인식, 빨강·주황 혼동)는 그대로 나타날 수 있습니다. "단계별 상태"와 "후보 판단" 탭에서 확인할 수 있습니다.
- 단계를 바꾸려면 `viewer_pipeline.py`에서 해당 함수만 고치면 됩니다.

  | 단계 | 함수 |
  |---|---|
  | 해석 | `Viewer._infer` 1단계 |
  | 탐지 | `_fresh_photo`, `_roi_dets` |
  | 역할 판단 | `_roles` |
  | 접근성 | `access` |
